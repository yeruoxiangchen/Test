# Studio 首轮评测协议 v1

本轮评估已实现的图片/短视频服务。配置在 `protocol.json`，生成前保存其 SHA-256、源代码摘要、模型 revision、ComfyUI revision、Python/torch/CUDA/驱动信息。源代码摘要只处理小型源码，不重新扫描或哈希权重。

## 依据与适用范围

| 部分 | 依据 | 本项目采用的方法 | 报告边界 |
|---|---|---|---|
| 图片内容遵循 | [GenEval 官方实现](https://github.com/djghosh13/geneval)、[论文](https://arxiv.org/abs/2310.11513) | 覆盖对象、数量、颜色、位置、属性绑定；每条提示词预写检查项 | 自定义 20 条提示词、每条 2 个种子，属于内部诊断集；不称为官方 GenEval 分数 |
| 视频质量 | [VBench 官方实现](https://github.com/Vchitect/VBench)、[论文](https://arxiv.org/abs/2311.17982) | 分开观察主体保持、背景稳定、运动、画质及提示遵循 | 自定义视频集不报告标准榜单总分；运动幅度与一致性需同时观察 |
| 图生视频 | [VBench++](https://arxiv.org/abs/2411.13503) | 同时核对输入主体保持和要求的运动 | 参考图使用本轮预先指定的 SDXL 输出，记录来源；结论不泛化为真实照片全集表现 |
| 延迟与吞吐 | [MLPerf Inference 规则](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc) | 固定任务、明确负载、区分逐任务延迟与饱和吞吐，记录端到端完成时间 | 未运行 MLPerf LoadGen 和官方任务，不称为 MLPerf 结果；P95 是本项目探索性指标 |
| 故障恢复 | 当前 API、持久化队列及 Worker 的行为约定 | 检查状态、重复执行、丢任务、定向取消、断连/重启恢复 | CPU 故障模拟器用于验证协议；不能替代 GPU OOM 和真实生成验证 |

80 条任务是首轮可执行的成本预算，不是文献规定的统计充分样本数。按提示词聚合两个种子的结果，保留失败任务，报告样本数；小样本不据此承诺可靠 SLA。更大规模的官方基准应另建协议，不在看到结果后修改当前集合。

## 固定任务与运行顺序

1. 三种模式各一条小规格功能测试：512²、6 步；视频 17 帧/16 fps。只验证链路，不用于正式质量或速度结论。
2. 40 张图片：20 条提示词 × 2 个种子，1024²、25 步、CFG 6。
3. 20 条文生视频：10 条提示词 × 2 个种子，1280×704、49 帧、16 fps、20 步、CFG 5。
4. 20 条图生视频：使用 i01–i10 的第一个种子生成的图片，各配预先指定的动作提示词 × 2 个种子。输入图失败时标记依赖失败，不挑另一张好图替代。
5. 单卡直接调用 ComfyUI 与经过工作台的配对比较：相同工作流和种子，按提示词交替 AB/BA 顺序，以两轮交错执行避免连续提交完全相同的采样节点。保留默认模型加载节点缓存，逐任务检查 `execution_cached`，一旦采样结果被复用则判为无效测量；不使用会一并禁用加载节点缓存的 `--cache-none`。
6. 1/2 卡吞吐比较使用相同固定图片任务集合，每卡一个 Worker；记录任务提交窗口、全部完成窗口及失败数。没有第二张独占卡时保持该项未完成。

正式测试使用独占空闲卡。运行期间持续记录 GPU 上的计算进程；若出现其他作业，该样本标记资源干扰，不纳入干净性能汇总，原始记录仍保留。不会结束其他项目进程。

## 测量定义

- API 接收：数据库 `created`；Worker 领取：`started`；推理起止：ComfyUI `execution_start` / `execution_success` 事件中的时间戳；作品就绪：终态更新时间；客户端观察完成另记。
- 排队时间＝Worker 领取－API 接收；ComfyUI 排队/分发时间＝真实执行开始－Worker 领取；执行时间覆盖加载、文本编码、采样、VAE 解码与编码节点；保存及轮询开销＝作品就绪－真实执行结束。
- 端到端时间＝作品就绪－API 接收；客户端观察时间含查询间隔，分别报告。没有真实执行事件的任务不得用领取时间冒充推理开始时间。
- 每秒采样 GPU 已用显存和该 Worker 的进程显存、CPU RSS。采样最大值是观测峰值，不是 CUDA allocator 的精确峰值。
- 成功必须同时满足服务终态成功、文件存在、完整解码、尺寸及视频帧数正确。超时、OOM、无效输出均保留并计失败；故意取消和非法输入属于单独故障测试。
- 冷启动、同模型连续运行、模型切换分别标注。首轮报告样本量、中位数、范围、经验 P95；不把不同任务规格混在一起算延迟。
- 吞吐＝固定窗口内有效完成的任务数/窗口时间；窗口从客户端提交开始，到全部文件下载并完整解码结束，包含验收开销。中断批次保留记录，新建完整批次计时，不能复用旧批次已完成任务虚增吞吐。多卡扩展效率＝多卡吞吐/(卡数×单卡吞吐)。

## 质量审查

为全部输出生成审查索引与视频取帧。文件可解码、像素变化、黑帧检测等属于自动诊断，不代表语义质量分数，也不等价于 VBench。

审查项：提示词逐项满足；主体/结构是否明显错误；视频动作是否发生；主体与背景是否稳定；图生视频是否保留参考主体。可用标准为主要请求满足且无严重结构错误。评审者、评分和理由必须记录。助手视觉审查应明确标注，不能称为独立人工盲评；没有实际评分时只交付审查材料，不填写虚构分数。

配对作品展示时隐藏方法名、随机左右顺序，并保留映射。源图、视频与评测产物均放在 `/data/zjr/aigc_studio/evaluations/`；源码目录仅保存协议、脚本和小型报告。
