## 工程改善与剩余实现问题

本轮9题实际取得可比较公开基线，优于v2同题的4题，且没有重复出现PyVista的公开渲染收集崩溃或动态参数ID误报。但预检10题ready不保证并发评测时仍全部可用：pvlib-1616预检约59.6秒完成17例，正式基线运行120秒超时，只输出16个进度点，没有完整JUnit结果。具体慢在JIT、CPU争用还是其他步骤，现有日志不能确定；不能把报告中的0题运行异常解释成每一次工具调用都健康。

控制器还有以下可定位的问题：

1. **“非复现文件”被当成了“有效实现改动”。** `workflow_feedback.py`的`source_changes`只排除已经注册的复现路径，没有区分实现、调试和诊断产物。SQLFluff留下8个debug/test脚本，即满足非空改动检查，`retry_needed=false`。`.sca_scratch/`确实会被排除，但只靠提示词不能保证模型把临时文件都放进去。修复应基于原仓库结构、已有文件和新增模块用途，不能依据隐藏参考补丁文件名设白名单。
2. **问题本身的验收没有形成稳定记录。** 所有10题均没有控制器验证过“原代码失败、当前代码通过”的固定复现。并非Agent完全未尝试复现：它运行了许多自写脚本，2次调用register_reproduction因指定文件不存在而失败，未形成有效记录。公开回归抽样与问题修复验证是不同证据，当前流程没有可靠吸收后者。
3. **主循环耗尽后可能直接收尾。** 配置60次调用，其中12次预留纠错，主循环实际48次。sqlfluff-1733、astroid-1092因phase_budget结束，控制器只看到“有改动、没有抽样回归”，未使用剩余纠错预算；astroid-1092工具日志中仍有A而非B的未解决现象。缺少固定复现不应自动当作回归，但也不能把未完成的修复任务当作可以正常提交。`passed=false`已被记录，系统没有把这些题误判为最终成功；问题在继续修复与交付条件。
4. **命令时间上限与任务时间不协调。** 单条bash允许600秒，占单题1200秒的一半；astroid-984的一次自写复现实际超时600秒。5题达到总时限，不能简单推断延长时间就能提高成功率，其中1题本来已正确，另5题在未耗尽时限时仍失败。

改进优先级应是：区分真实实现改动与调试产物；保存问题级自测的实际返回值、断言和前后版本；在保留连续工具循环的同时，令明确未解决的状态参与停止/纠错判断；缩短可中断诊断命令的默认时限并预留最后验证时间。这是可直接从轨迹定位的执行问题，无需先训练RL或OPD。

## 模型能力、定位与基准的边界

9题通过read_file读过参考修复相关文件，8题修改过至少一个相关文件；9份失败补丁中7份也有修改文件交集。交集不等于定位正确，但说明不能把失败全部归因于检索不到文件。跨模块修改不完整、对现有API兼容性判断错误、明明反馈失败却继续声称成功，都是已观察到的模型行为问题。

模型请求等待合计约2.62小时，占逐题时间合计约87.9%；这是包含排队、prefill、生成和通信的累计等待，不是GPU内核计算时间，也不是用户等待时间。共享四卡和缩短后的20分钟预算可能限制探索，但没有独占同条件对照，不能把9题失败归咎于共享卡。

至少marshmallow-2123、pvlib-1616存在明确的题面/隐藏验收接口差异，pyvista-4329也涉及原问题未完整说明的最终接口语义。这些样本保留原分数并单列解释，不能擅自改判成功，也不宜当作无歧义的训练奖励。特别是pvlib-1616，Agent实现的是题面明确建议的新函数，不能仅凭隐藏测试未通过断言“它没有按需求实现”。

## 下一步判断

当前结果支持保留已验证的环境与公开反馈修复，但还不足以证明自写工作流具备稳定的真实修复能力。不建议立刻扩回100题或加入RL/OPD。先针对上述可复现的提交/反馈缺口做离线验证，再在同一批10题、同模型和明确一致的预算下运行已经接入的mini-SWE-agent作为对照；目前没有该对照的正式成绩。

这个对照用于决定继续维护当前编排还是改用现成执行器，不能预先保证mini会更高。已经分析过的10题用于工程回归，后续独立评测应另留未用于修改流程的任务，避免把这批诊断集的提升当作泛化效果。本次仅离线分析，没有新训练、模型调用或仓库测试。
