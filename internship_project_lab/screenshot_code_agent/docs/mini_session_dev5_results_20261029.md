## 本轮仍暴露的接入与控制问题

### 1. 一个坏工具参数会中断整题，而且错误被误分类

pydicom第72次模型响应的bash命令包含真正的NUL字符（JSON中的`\u0000`解码后成为空字节），不是普通文本`\\x00`。`MiniEnvironment.execute`将其直接传给`Sandbox.run`，`subprocess.Popen`在启动命令前抛出`ValueError: embedded null byte`。

冻结执行器没有将这个参数错误转成工具失败反馈，外层`harness_runner`笼统记为`model_error`后结束Agent。证据是72次模型请求/响应、72次工具开始，但只有71次工具结果；没有模型API错误事件。这是模型生成了无效工具参数，同时本地接入没有实现可恢复处理，不能解释为推理服务断线。

原报告的`runtime_failures=0`仅覆盖特定基础设施错误，不含这个分支。因此保留原报告的同时，审计单独记录`agent_exception_tasks=[pydicom-793]`，不能宣传“零运行故障”。恢复此异常只能让模型继续尝试，不能证明它一定能修好此前已删坏的函数。

### 2. 提交检查只在主动提交时发生，异常或额度结束没有通过检查的候选兜底

本轮3题主动提交，3题都在第一次提交时通过当前检查，随后全部正式评分失败；marshmallow和pydicom没有`delivery_check.json`，直接评分退出时的候选。

当前实现并非“所有最终候选都验收通过”，也未保存/恢复最后一个通过公开检查的候选。原先65项基础检查、48项真实环境检查验证了约定的执行场景，没有覆盖空字节命令恢复，也不能证明生成补丁正确；此前用它们作为整套流程可靠性的依据仍不充分。

### 3. 检查与真实行为要求不一致，模型可以忽略已经看到的失败

- **PyVista**：公开脚本只验证`faces`的替换，以及`cells`只读，没有验证`grid.cells = ...`。模型自己的复现已两次报setter错误，最后却将“原来没有setter”解释为可以忽略，再提交成功。轨迹并非没收到反馈，而是错误判断了反馈；我们也没有设置相应的行为门槛。
- **pvlib**：公开脚本绕过正常构造，使用`object.__new__(ModelChain)`检查推断方法名。它没有覆盖显式构造、可选参数转发和无效模型报错，因此不完整补丁也能通过。模型运行了16个既有AOI测试，但之后两条点名测试命令均因找不到测试返回4，它依然提交。
- **astroid**：该题没有额外开发断言。模型已经看到相关测试失败，却认为“行为稍有变化，解决崩溃更重要”。只验证不崩溃，不能验证相对导入应返回正确布尔结果；语法/导入检查自然无法拦住。
- **marshmallow**：按行号多次`sed`删除/插入后，函数所属类改变；模型看到实例化失败，却继续局部编辑直到96次额度耗尽。没有及时恢复一个验证过的完整候选。

这批证据指向“编辑后行为验证、失败处理与候选保留”仍然薄弱。需要修复接入异常，也需要加强修复流程；不能把所有失败归咎于模型、mini上游或运行环境。
