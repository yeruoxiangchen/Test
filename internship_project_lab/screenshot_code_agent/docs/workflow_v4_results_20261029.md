## 改动哪些有效，哪些仍然不足

1. **公共反馈链路更稳定。** 本轮10题均获得可比较的公共基线，包括上次超时的pvlib-1616；该题公共基线取得14个通过状态。没有再出现公共检查inconclusive。9题的新增断言在真实运行的原代码上均能复现失败。
2. **未修好的问题能触发纠错，但不保证纠正。** SQLFluff实际执行两轮纠错，共86次模型调用；其中18次edit_file调用指向L003.py，最终输出仍不对。pydicom-816在通用编码断言失败后进入纠错，新增了错误捕获，但又引入坏字节处理错误。不能说重试没有运行，也不能说运行了重试就有效。
3. **新增验收覆盖不足，这是这轮实现的责任。** 最终9个已知问题断言中5个通过，仅其中pydicom-793完整通过最终评分。PyVista脚本只检查faces setter和cells只读，漏掉cells setter；marshmallow-1702只测混用参数时警告，漏掉旧kwargs单独使用；pvlib-1832直接调用PVSystem和infer_aoi_model，绕过ModelChain显式构造入口，也没检查可选参数透传；marshmallow-2123没覆盖两种URL都禁用的参数组合。
4. **不能把断言验证过当成验收覆盖完整。** 之前“9/9断言能区分原代码与参考源码”的CPU检查只证明存在一个可复现差异，不能证明能排除所有不完整补丁。PyVista、marshmallow-1702、pvlib-1832均被当前公共检查标记passed，最终仍失败；这三次过早放行是实证。
5. **时间预算未给纠错保留可用空间。** pvlib-1616和astroid-1092在主循环约26分钟处触发为最终检查预留240秒的阈值，随后重试条件也因剩余时间不足被跳过。它们只用了24、55次调用，未接近96次上限；仅增加调用上限没有用。应把最后验收时间与至少一轮纠错时间分别安排，而不是都挤在收尾阶段。
6. **仍有无效开销与诊断产物遗漏。** astroid-984最终正确，但因未注册有效复现被再次要求修复，最终补丁没有变化。PyVista交付仍含final_verification.py，说明按文件名识别临时脚本的启发式并不完整；不能声称临时文件污染问题已全面解决。

核对pydicom-816、SQLFluff、astroid-1092和pvlib-1616首末真实模型请求，开发要求和固定断言均存在，不能把失败归结为“提示没有传给模型”。模型对反馈的使用、跨模块修改完整性和终止条件仍有问题。

10题累计模型请求等待约2.90小时，占逐题耗时合计约89.9%。这是含排队、prefill、生成和通信的等待时间，不是纯GPU计算时间；没有独占对照，不能认定是共享GPU或home盘负载造成修复失败。最终日志已经给出具体实现错误。
