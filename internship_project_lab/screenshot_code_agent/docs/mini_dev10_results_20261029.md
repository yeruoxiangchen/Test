## 适配层的确切问题

### 1. 跨命令临时文件消失

冻结版本`runtime.py`的`OCISandbox.command()`每次加入`--tmpfs /tmp`，`sandbox.run()`每次重新启动Bubblewrap。故`/testbed`持久，但`/tmp`只活到单条命令结束。上游mini的Docker环境是启动同一容器后反复`docker exec`，目录切换不持久不等于文件不持久。

本轮3题共7条反馈明确显示`/tmp`路径不存在：marshmallow-2123三条、PyVista三条、pydicom-793一条。例：PyVista的`conversation.json`零基索引16写`/tmp/reproduce_issue/reproduce_issue.py`、17返回0、18执行该目录下脚本、19就报目录不存在；重写后索引23再次报文件不存在。pydicom-793索引28写`/tmp/fix_test.py`、29返回0、31报文件不存在。

已用本轮冻结源码和同一OCI环境做独立CPU复现：第一条命令同时写`/tmp/sca_probe.txt`与`.sca_scratch/sca_probe.txt`，返回0；第二次读取前者返回1/不存在，第三次读取后者返回0/内容正确。没有执行模型或候选修复代码。证据见`tmp_lifetime_probe/result.json`。

此前提示建议用`.sca_scratch`，但提示不能替代正常文件持久语义。此问题直接干扰复现和验证，尚没有反事实重跑证明修掉后会增加几题成功。

### 2. 常用回滚操作被只读.git阻止

marshmallow-2123的conversation索引46—47，以及pvlib-1832的76—77：模型执行`git checkout ...`恢复源码，均得到`index.lock: Read-only file system`。工作目录文件是可写的，但git操作需要更新索引；当前边界阻断了回滚。

这两题最后均存在语法问题。模型自身的按行修改、失败后的处理仍有责任；但环境没有提供等价易用的恢复能力，不能把整个失败过程算作mini算法的问题。后续应给任务自己的Git状态或受控restore提供可用路径，同时保持独立基线、受保护测试及最终评分隔离。

### 3. 交付范围与上游不同，备份文件全部进入补丁

10/10题交付包含`.backup`、`.bak`等备份；另外还有`.fixed`、`.temp`、临时函数文本及`test_fix.py`。这不是10个空补丁，但也不能把新增备份计为有价值的实现。上游流程要求挑选源码生成patch；我们的适配从整个工作区导出diff，仅靠`.sca_scratch`提示没有阻止污染。

应明确交付文件范围、检查备份和复现文件，再从可信基线验证真正源码修改。不能直接相信模型给出的“已经修好”文字，也不能简单排除所有新文件，因为正确实现也可能新增源码。

## 环境之外仍然存在的问题

- **固定提示并未丢失。** 九道带开发提示的任务，最后一次真实模型请求仍包含这些提示；无法把失败统一解释为上下文压缩丢掉要求。
- **可见失败不等于会自动解决。** astroid-1092明确输出A而非B，最后断言也失败，模型仍决定提交；pvlib-1832最后import报SyntaxError后提交。mini原循环把提交信号视作退出，并没有自动证明补丁正确。
- **测试覆盖不足会给出错误信心。** PyVista的自建“全面测试”仍漏cells setter，pydicom-793只覆盖部分ASCII边界，marshmallow-1702只跑旧测试/不完整自测。部分测试只是打印FAILURE或捕获异常后正常退出，返回0不能当作行为通过。
- **重复编辑仍会消耗预算。** SQLFluff最终只留下注释，astroid-1092只包裹相同推断逻辑；这类问题不能靠增大调用上限自动解决。718次调用没有换来更多成功。

所以本轮确定的是“当前接入版本没有收益，并暴露具体适配与修复缺口”，而非“成熟框架也无效”或“模型已经没有提升空间”。这仍是10道已知开发题、单次运行，且没有截图输入。

## 建议的下一步顺序

1. 先修环境契约：每题独立且跨命令保留的`/tmp`，实际可用的源码回滚；用写→读→执行、修改→回滚→再次导入的小测试验证。存储仍落`/data/zjr`，不暴露主机共享临时目录。
2. 完善交付检查：捕获源码语法/导入失败、备份混入、只有注释或无行为变化；公开断言失败时给出清楚反馈。最终评分仍在Agent退出后运行，不向模型泄露参考测试。
3. 修正开发验证覆盖：setter与getter成对、旧接口警告、真实构造入口、参数组合、ASCII/非ASCII边界。不同流程保持相同可见信息，新增检查不能只给其中一个框架却宣称公平提升。
4. 再运行原10题，不删失败题；先判断环境修复和反馈是否有效，再考虑更强模型的小规模上限检查或RL/OPD。现阶段不适合拿不完整验证信号直接当训练奖励。

此次只完成离线分析、原沙箱CPU复现和归档，没有修改修复器、覆盖历史分数或启动新模型评测。
